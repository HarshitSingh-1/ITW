Member 1: Harshit (Team Lead)

Cloud Architecture & Database

Harshit — Cloud Architect & Database Lead

Supabase • PostgreSQL • Vercel

Assigned Production Scope: Supabase Database Tables (events, tickets, profiles, reviews, discussions, event_gatekeepers), PostgreSQL Stored Procedures (RPCs), Row-Level Security (RLS) Policies, and Vercel Cloud Secrets.

🔍 Exact Code 1: Stored Procedure book_ticket_safe (PostgreSQL / Supabase)
SELECT total_capacity, tickets_sold INTO v_cap, v_sold FROM events WHERE id = p_event_id FOR UPDATE; IF v_sold >= v_cap THEN RETURN FALSE; END IF; UPDATE events SET tickets_sold = tickets_sold + 1 WHERE id = p_event_id; INSERT INTO tickets (event_id, student_email, qr_code_string, is_scanned) VALUES (p_event_id, p_student_email, p_qr_string, false); RETURN TRUE;
What this does: FOR UPDATE places an exclusive pessimistic row lock on the event record. If 100 students click Book at the same millisecond for the last ticket, the database queues them and only lets the first transaction decrement the seat, completely preventing double-booking.
🔍 Exact Code 2: Stored Procedure assign_event_gatekeeper (PostgreSQL / Supabase)
What this does: Uses SECURITY DEFINER to grant junior student volunteers permission strictly to read and verify tickets for one specific event ID without giving them full admin access to delete events or view financial records.
🎙️ What Harshit Says in the Presentation:
"I built the cloud backend on Supabase and Vercel. I engineered our atomic seat booking using PostgreSQL pessimistic row-level locks (FOR UPDATE), which mathematically guarantees that overselling and double-booking can never happen. I also enforced Row-Level Security policies to protect student data privacy."
Teacher: "How did you prevent race conditions and double-booking in the database?"
Harshit: "We wrote a PostgreSQL stored procedure named book_ticket_safe that executes with SELECT ... FOR UPDATE. This locks the specific event row during transaction execution. Any concurrent request arriving at the same millisecond is queued. Once the first ticket commits, the next request reads tickets_sold >= total_capacity and returns false, triggering our automated refund."
