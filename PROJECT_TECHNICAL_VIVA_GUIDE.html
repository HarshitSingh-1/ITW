1. Core Application Framework: app.js

Client Architecture

app.js serves as the central orchestration nervous system of the entire client-side application. It is loaded globally across all five web interfaces (index.html, wallet.html, history.html, admin.html, scanner.html) to manage authentication lifecycles, user identities, theme preferences, and cross-device navigation.

A. Supabase Auth State Machine (onAuthStateChange)

Instead of relying on fragile manual cookie inspection or polling localStorage on interval loops, app.js subscribes to an asynchronous reactive event listener provided by the Supabase Client SDK.

  • Reactive Lifecycle: Emits real-time state transitions: SIGNED_IN, SIGNED_OUT, TOKEN_REFRESHED, and USER_UPDATED.
  • Zero-Reload State Transitions: When a user logs in or out in another tab, the current tab reacts instantly, invalidating cached credentials and updating navigation controls.
  • Automated Profile Hydration: Upon receiving a valid JWT access token, it queries the PostgreSQL profiles table using auth.uid() to fetch student metadata (Full Name, College, Roll Number, Branch, and Access Role).

B. Persistent Theme Engine (Dark & Light Mode)

Provides seamless contrast switching without page flicker (FOIT). The engine reads cached settings from localStorage.getItem('theme') and checks the hardware device's OS preference via window.matchMedia('(prefers-color-scheme: dark)'). It dynamically attaches or strips the .dark class on document.documentElement, driving Tailwind CSS dark mode utilities across all templates.

C. Global Mobile Drawer Navigation Orchestration

Addresses mobile responsiveness where desktop headers (hidden md:flex) are constrained. initMobileNavigation() binds touch event listeners to #mobile-menu-btn, smoothly toggling the height and opacity of #mobile-menu while synchronizing the user's active session badge into .user-email-mobile.

🎓 Key Viva Defense Point (app.js)
"We implemented an event-driven decoupled architecture. UI components never directly mutate user state; they react to auth events emitted by the Supabase client state machine. This guarantees zero state drift across tabs and views."

2. Main Portal: index.html

Discovery, Concurrency & Community

A. Multi-Dimensional Client-Side Filtering Pipeline

To guarantee 0ms latency for students searching for events, all active events are queried once on page load and held in an in-memory collection (allEvents). As the student types into the search field or clicks category chips, a compound intersection filter executes client-side:

FilteredList = Events.filter(e => (e.title.includes(q) || e.desc.includes(q)) && (selectedCategory === 'all' || e.category === selectedCategory) && (selectedCollege === 'all' || e.college_name === selectedCollege) && (selectedPrice === 'free' ? e.price === 0 : true) );

B. Atomic Seat Booking via PostgreSQL RPC (Pessimistic Row Locks)

The Critical Flaw of Naive Systems: In high-demand college fests, 50 students simultaneously click "Book" for the last remaining seat. In basic web applications, 50 queries execute SELECT available_seats, find 1, and write 50 tickets—causing catastrophic double booking.

Our Solution (ACID Guarantee): We developed an atomic Remote Procedure Call (RPC) in PostgreSQL named book_ticket_safe:

CREATE OR REPLACE FUNCTION book_ticket_safe(p_event_id UUID, p_user_id UUID) RETURNS JSON AS $$ DECLARE v_seats INT; BEGIN -- Place an exclusive pessimistic row-level lock on this specific event record SELECT available_seats INTO v_seats FROM events WHERE id = p_event_id FOR UPDATE; IF v_seats <= 0 THEN RETURN json_build_object('success', false, 'error', 'SOLD_OUT'); END IF; -- Decrement seat count and issue ticket in one atomic transaction UPDATE events SET available_seats = available_seats - 1 WHERE id = p_event_id; INSERT INTO tickets (event_id, user_id, is_scanned) VALUES (p_event_id, p_user_id, false); RETURN json_build_object('success', true); END; $$ LANGUAGE plpgsql;

C. Race Condition Detection & Instant Auto-Refund Modal

1 Student completes payment through Razorpay modal; bank debits money and returns Payment ID.
2 Client invokes book_ticket_safe. If another transaction took the final seat, RPC throws 'SOLD_OUT'.
3 Client immediately fires POST /api/refund-payment with the captured Razorpay Payment ID.
4 Backend instructs Razorpay API to process an Optimum Speed Instant Refund.
5 The #soldOutRefundModal appears on screen, displaying transaction reference and refund confirmation.

D. Verified Attendee Review Gating

To eliminate trolling and fake feedback, ratings are strictly gated by proof of physical presence. The submission handler executes an inner join: tickets.user_id = auth.uid() AND tickets.is_scanned = true. Only attendees whose QR was physically verified at the gatekeeper checkpoint are authorized to submit star ratings and testimonials.

E. Nested Discussion Boards with Role-Based Access Control (RBAC)

Real-time Q&A threads linked to each event allow attendees to clarify logistics. Delete capabilities (🗑️) are restricted: only the original comment author (matching auth.uid()) or system administrators can delete comments, enforced at the database level by Row-Level Security (RLS) policies.

F. Crowdfunding Campaign Engine

Enables senior student bodies and collegiate clubs to raise funds for cultural festivals (Navratri, Farewell) or robotics competitions. Features real-time progress calculations ($\frac{\text{Current}}{\text{Target}} \times 100$), animated progress bars, and a dynamic modal accepting arbitrary contribution amounts directly into the Razorpay payment pipeline.

3. User Ticket Vault: wallet.html

Digital Passes & Export

A. Perforated Stub UI Geometry

Renders tickets using visual metaphors from physical event stubs. Built with pure Tailwind CSS and CSS pseudo-elements: radial cutout gradients simulate round punch holes on the top and bottom borders, separated by a vertical dashed tear border (border-dashed border-slate-700).

B. Client-Side Cryptographic QR Generation

Using QRCode.js, tickets generate scannable 2D barcodes entirely inside the browser canvas. Crucially, the QR code encodes **only the immutable 128-bit UUID** of the ticket row. Because the payload contains no raw personal data, a student cannot forge a pass by modifying local HTML or images.

C. Zero-Dependency Google Calendar Integration

Formats RFC 5545-compliant URLs opening calendar software directly:

https://calendar.google.com/calendar/render?action=TEMPLATE &text=Event+Title &dates=20261025T043000Z/20261025T083000Z &details=Hall+B+Workshop &location=Main+Auditorium

D. Verified Attendance Badge & Certificate Unlocking

If ticket.is_scanned === false, the ticket reflects a ⏳ Pending Check-in badge and the certificate button is disabled. Once checked in by the gatekeeper, the state switches to ✅ Verified Attendee, dynamically lighting up the certificate download option.

E. High-Resolution DOM Rasterization via html2canvas

Enables students to save passes offline for network-dead venues (basements, auditoriums). html2canvas traverses the ticket card's DOM tree, compiles computed styles, renders at scale: 2 (Retina DPI), and triggers a clean PNG download.

4. Attendance & Archive Portal: history.html

Audit & Verification

A. Temporal Participation Classification (Attended vs Missed)

Past events (where event_date < NOW()) are partitioned based on physical check-in status:

  • Attended (Green Badge): The ticket was scanned at the gate (is_scanned === true). Full access to participation certificates is unlocked.
  • Missed (Grey Badge): The seat was booked but the student was absent (is_scanned === false).

B. Anti-Tamper Certificate Lock

Events marked as Missed permanently lock the certificate trigger (🔒 Certificate Locked - No Attendance Record). This prevents students from claiming participation credentials or extra academic credits for events they skipped.

C. Organizer Post-Event Retrospective Analytics

For faculty coordinators and club leads, history.html renders aggregate yield metrics:

Turnout Rate (%) = (Scanned Tickets / Total Tickets Sold) * 100 Capacity Fill (%) = (Total Tickets Sold / Total Event Capacity) * 100

5. Organizer & Admin Dashboard: admin.html

Management & RBAC

A. Security-Definer Gatekeeper RPC (Privilege Minimization)

The Problem: Event organizers need student volunteers to scan tickets at entry doors. However, granting volunteers administrative privileges creates massive vulnerability (volunteers could alter prices, delete events, or view financial records).

The Solution: A PostgreSQL stored procedure declared with SECURITY DEFINER:

CREATE OR REPLACE FUNCTION assign_event_gatekeeper(p_event_id UUID, p_email TEXT) RETURNS JSON SECURITY DEFINER AS $$ DECLARE v_target_user_id UUID; BEGIN -- Lookup target user by email SELECT id INTO v_target_user_id FROM auth.users WHERE email = p_email; IF v_target_user_id IS NULL THEN RETURN json_build_object('success', false, 'error', 'USER_NOT_FOUND'); END IF; -- Grant scanning authorization strictly scoped to this single event ID INSERT INTO event_gatekeepers (event_id, user_id) VALUES (p_event_id, v_target_user_id) ON CONFLICT DO NOTHING; RETURN json_build_object('success', true); END; $$ LANGUAGE plpgsql;

B. Demographic Visualizations via Chart.js

Executes relational joins across tickets and profiles to render real-time demographic breakdowns:

  • Gender Ratio: Donut chart highlighting diversity metrics across attendees.
  • Department / Branch: Vertical bar chart displaying registration distribution across Computer Science, Electronics, Mechanical, Civil, etc.
  • Academic Year: Polar area chart tracking 1st through 4th-year student engagement.

C. Dual-Mode Sanitized CSV Exporter

Allows organizers to export verified attendance rosters. Features **CSV Formula Injection Sanitization**: any cell data beginning with potentially harmful spreadsheet calculation operators (=, +, -, @) is prepended with a single quote (') to prevent Remote Code Execution in Microsoft Excel. Timestamps are formatted into Indian Standard Time (IST).

D. Supabase Storage Poster Pipeline

Handles raw image file streaming directly to the event-posters bucket via Supabase Storage API, returning a persistent public CDN URL saved to events.image_url.

6. Gatekeeper Scanner: scanner.html

Hardware Scanning & Concurrency

A. WebRTC Rear Camera Feed Acquisition

Interacts with hardware optical sensors using standard WebRTC APIs:

navigator.mediaDevices.getUserMedia({ video: { facingMode: "environment", width: { ideal: 1280 } } });

The constraint facingMode: "environment" explicitly forces mobile browsers to activate the high-fidelity rear camera sensor instead of the front-facing webcam.

B. Frame Mutex Concurrency Lock (isProcessing)

The video stream decodes frames at 60 FPS using requestAnimationFrame. When an attendee holds a QR code before the lens, a naive loop would trigger 60 duplicate network requests within a single second. To prevent database flooding, an atomic boolean flag isProcessing = true locks the stream immediately upon first decode, discarding all subsequent frames until an asynchronous 2-second cooldown concludes.

C. 5-Step Verification & Validation Pipeline

1 Regex UUID Validation: Verifies format ^[0-9a-f]{8}-[0-9a-f]{4}...$ before executing database queries.
2 Authorization Check: Confirms the scanning user is registered as the Organizer or an assigned Gatekeeper.
3 Duplicate Verification Gate: If ticket.is_scanned === true, plays an error tone and renders a RED alert: "ALREADY USED at [Timestamp]".
4 Atomic Mark Mutation: If unverified, updates is_scanned = true, scanned_at = NOW().
5 Audible & Visual Confirmation: Plays success chime, displays student name, roll number, and branch on screen.

7. Zero-Backend Certificate Engine: certificate.js

Vector Graphics & Mathematics

A. Client-Side High-DPI Vector Rasterization

Traditional applications generate certificates on the server using headless browsers (Puppeteer), consuming excessive CPU/RAM and incurring cloud costs. Our engine creates an in-memory HTML5 <canvas> element dimensioned at 1600 × 1130 pixels (~300 DPI print quality). The browser renders the entire document locally in under 80 milliseconds.

B. Procedural Mathematics & Anti-Counterfeiting

  • Parametric Guilloche Rosette: Mathematical curves generated using polar trigonometry: $$r = a \cdot \cos(k \cdot \theta)$$ Renders complex geometric security seals that cannot be easily replicated or altered.
  • Smooth Bézier Signatures: Uses cubic Bézier curves (ctx.bezierCurveTo()) to render lifelike digital signatures for authorizing officials.
  • Cryptographic Verification Watermark: Embeds the Ticket UUID at the footer, allowing anyone to verify physical printed certificates against the online database.

8. Serverless Payment & Refund APIs (/api)

Financial Cryptography

A. Order Initialization: api/create-order.js

A Node.js serverless microservice deployed on Vercel. Its primary responsibility is API Secret Encapsulation: RAZORPAY_KEY_SECRET is stored in server-side environment variables and is never exposed to the client. Converts Indian Rupee amounts to smallest integer units (paise: ₹100 = 10,000 paise) and invokes razorpay.orders.create().

B. Cryptographic Signature Verification: api/verify-payment.js

The Threat: A client could tamper with JavaScript in DevTools and fake a success response without paying.

The Mathematical Proof: When Razorpay captures payment, it hashes the transaction data using the merchant's secret key:

const expectedSignature = crypto .createHmac('sha256', process.env.RAZORPAY_KEY_SECRET) .update(order_id + "|" + payment_id) .digest('hex'); if (expectedSignature === razorpay_signature) { // Payment is mathematically authentic! }

C. Automated Instant Refund Pipeline: api/refund-payment.js

If a ticket sells out during payment transit, this microservice executes an immediate refund via Razorpay's API:

POST https://api.razorpay.com/v1/payments/{payment_id}/refund Headers: { Authorization: "Basic [Base64(Key:Secret)]" } Body: { "speed": "optimum" }

Passing "speed": "optimum" guarantees instant reversal via UPI/IMPS rails directly back to the student's original payment method.

9. Viva Defense & Technical Interview Master Q&A

Examiner Cheat-Sheet
Q1: How does your system prevent two students from booking the last ticket simultaneously?
Answer: We implemented a PostgreSQL stored procedure named book_ticket_safe that executes with SELECT ... FOR UPDATE. This places an exclusive pessimistic row lock on the event record during the transaction. Concurrent requests must wait in a queue; once the first request claims the ticket, subsequent transactions read available_seats = 0, abort immediately, and trigger our automated instant refund flow.
Q2: Why not just store the student's name and event title in the QR code?
Answer: Storing readable text in QR codes is insecure because anyone could generate a fraudulent QR with their name using a free generator. Instead, our system encodes only the cryptographically random 128-bit Ticket UUID. The scanner at the gate performs an authenticated database lookup against that UUID to confirm validity, gatekeeper authorization, and scan state.
Q3: What happens if payment succeeds on the user's bank app but the seat is gone?
Answer: We have an automated circuit-breaker refund engine. When the client catches the 'SOLD_OUT' exception from the database RPC, it immediately dispatches the Razorpay Payment ID to /api/refund-payment. Our backend calls Razorpay's API with speed: "optimum", reversing the funds instantly back to the student's UPI or card without requiring manual admin intervention.
Q4: How do you prevent student volunteers from abusing their scanning access?
Answer: We enforce the Principle of Least Privilege using a SECURITY DEFINER RPC named assign_event_gatekeeper. Volunteers are granted scoped access exclusively to read and update the is_scanned status for their assigned event ID. They have zero permissions to delete events, view student financial histories, or modify ticket counts.
Q5: Why did you build certificate generation in client-side Canvas instead of a backend PDF library?
Answer: Server-side PDF generators like Puppeteer launch headless Chrome instances on the server, consuming 150–300MB of RAM per document and creating massive CPU bottlenecks during large fests. Our client-side Canvas engine offloads all vector math, guilloche rosettes, and Bézier curves to the user's browser GPU, rendering a 300 DPI print-ready certificate in under 80 milliseconds with zero server cost.
Q6: What stops an attacker from submitting a fake payment confirmation from browser console?
Answer: The frontend never decides whether a payment is valid. Instead, the raw transaction payload is sent to our serverless endpoint /api/verify-payment. The server computes an HMAC-SHA256 signature using our private Razorpay Secret Key. If the generated hash doesn't match the signature provided by Razorpay character-for-character, the request is rejected as tampered.
Q7: How do you protect against CSV Formula Injection when exporting attendee lists?
Answer: In admin.html, our export function sanitizes all string values. If any user-inputted field (like student name or roll number) begins with formula trigger characters such as =, +, -, or @, we prepend an apostrophe ('). This ensures spreadsheet programs like Excel or Google Sheets treat the cell strictly as raw text rather than executing arbitrary macros.
Q8: How does the camera scanner handle 60 frames per second without crashing the database?
Answer: We implemented an asynchronous concurrency mutex lock using a boolean flag (isProcessing). The instant a valid QR payload is decoded, isProcessing is set to true. All subsequent video frames decoded by requestAnimationFrame are instantly discarded until the network verification completes and a 2-second debounce timer releases the lock.
Q9: What is the architectural role of Row-Level Security (RLS) in your application?
Answer: Supabase connects the client directly to PostgreSQL. Row-Level Security ensures that even if a student inspects our API keys or manipulates network requests, the PostgreSQL engine itself blocks unauthorized queries. For example, an attendee can only SELECT tickets where tickets.user_id = auth.uid(), preventing students from inspecting each other's tickets.
Q10: How does the Crowdfunding module differ technically from standard event ticketing?
Answer: Event ticketing operates on fixed-unit inventory with deterministic seat decrements. Crowdfunding operates on dynamic variable contributions without inventory limits. The donation modal allows contributors to inject variable financial amounts into the Razorpay order creation microservice, updating aggregate campaign progress metrics in real time.
